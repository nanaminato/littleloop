### 重复派发及正确结果误判

- `cb14588f` #17 与 #19 的 `instruction` 文本完全相同，分别产生不同的派发 ID。首次回执 #18 已正确给出 `f891`。`ba632f53` #10 与 #12 也复用完全相同的指令，首次回执 #11 已正确给出 `5801`。两次都是 Bot 在有效回执之后提交了新的委派。
- `57546343` #21 声称 `0716` 与原始编号末四位不符，而 #20 的 `0716` 已匹配。#28 的说明同时给出回执值和相同的期望值 `7901`，仍发出复核。这表明重复既包含相同指令，也包含带错误复核理由的不同指令。独立验证器能核对字符串相等，草稿的自由文本没有给宿主一个可机械验证的业务证据条件。

### 归纳出的确定性回归输入

历史草稿缺失，以下注入输入只复现数据可证实的校验与状态边界。采用通用目标与虚拟执行器标识，生产决策器无需识别历史任务名称。

| 回归边界 | 注入条件 | 验收行为 |
| --- | --- | --- |
| 同目标和定时约束 | 回执触发当前目标，注入其他目标 ID、该事件不允许的动作、越界延迟或给非 `Wait` 动作附带延迟。 | 不执行草稿，区分字段与原因，向模型返回当前目标的合法选项。合法的后续 `Wait` 才能预约。 |
| Harness 引用 | 分别注入缺值、未知 ID、唯一等值的大小写或空白变体。 | 未知 ID 不能替换成任意已注册执行器。唯一等值规范化保留原值及修复记录。 |
| 已有正确证据 | 一次已完成派发保存可独立核对的结果，后续草稿重复相同指令，或另写指令声称有矛盾。 | 允许 Bot 有证据地复核。投影保留先前派发、来源和验证状态，复核留下可审计理由。 |
| 修订竞态 | 草稿正在修复时推进目标版本，保留旧派发日志及工具证据。 | 旧草稿不能提交，证据仍标记来源版本。下一次判断以新快照为准。 |
| 在途崩溃 | 确认真实派发日志已进入提交状态，宿主在结算前退出并重启。 | 使用同一派发标识查看原生证据。缺少确定结果时进入核对，不能重发或伪造完成。 |

## 决策修复

同一个 `IBotDecisionEngine` 仍负责下一步。模型适配器先解析单个 JSON 对象，再用 `BotDecision.Check` 区分 JSON、字段、Harness 引用、目标版本和证据冲突。宿主提交门检查当前会话权限、目标版本和待处理用户消息。退回模型的结构化反馈包含错误码、涉及字段、当前合法动作、目标范围、可用执行器和可用的延迟范围。模型据这些条件重新提案，生产每次判断最多请求三份草稿。有修订或权限变更时停止旧判断。

局部规范化限于单一 JSON 代码围栏、唯一注册标识的空白或大小写、绑定目标的事件中缺省的目标 ID。错误目标、未登记的执行器和矛盾证据仍需重新判断。旧版本记录中的空值保持未知。每次请求记录原稿、规范化步骤、错误及用量，超出 65,536 字符的原稿只留长度及摘要。服务商在返回可解析草稿前拒绝的请求只留请求级诊断。成功及失败决定附在现有事件账本；过期或拒绝提交另存同账本的 `DecisionAudit`。这些原稿不会进入认知历史或普通聊天接口，数据库仍需按私聊数据管理。进程在事务之前硬退出时，内存中尚未落库的草稿可能丢失。[决策契约](../src/LittleLoop.Core/BotDecision.cs) · [模型适配器](../src/LittleLoop.Tools/ModelBotDecisionEngine.cs) · [提交门与审计](../src/LittleLoop.Chat/Bot/BotDecisionStore.cs)

三次草稿均未过校验时，目标等待人工处理，审计保存失败原因。对于明确的暂时服务错误，如超时、断线、限流或常见 5xx，已有且仍可定时的目标可以借现有 Timer 在 30 秒后重新判断一次。该技术等待不派发 Harness，同一次暂时故障再次触发时转为人工等待。未知执行仍沿用待核对流程。[宿主回退](../src/LittleLoop.Chat/Bot/ChatBot.cs)

候选试次 1 的事件 29 显示了旧日志无法辨认的一类错误。首稿是 `Delegate`，同时带 `wakeAfterSeconds: 30`。它因 `wake-requires-wait` 被拒。模型第二次仍选 `Delegate`，删除了延迟字段，随后跳过该等待并完成实质产出。这是一次协议修复成功和一次用户要求遗漏。该证据只说明此候选试次，无法反推旧版四份缺失的原稿。

候选试次 2 的同一阶段首稿已是合法委派，仍遗漏定时等待。试次 3 的同类组合字段错误则在下一稿改成合法 `Wait` 并保留了延迟。候选试次 5 的事件 14 选择 `Reply`，声称已经记下用户的补充流水号，目标要求却保持空数组。随后 Bot 完成任务时漏掉流水号和定时，驱动等待有效修订超时。最后一例是语义判断失败，驱动可以更早诊断该状态，当前结果仍计为失败。

## 证据与执行器

证据投影从目标的现有事件中读取最近最多 20 个派发，提供派发 ID、来源、目标版本、执行边界和结果样例。执行终结、获得观察、Bot 明确评估和整个目标完成分别表达。旧记录缺少必要标识或版本时保留未知；窗口截断也有标记。Bot 可在决定中提交 `verifyDispatchId` 记录评估。原指令在同一目标和 Harness 上完全重复且已有评估时，宿主要求明确 `reviewDispatchId` 及理由。新增要求、矛盾和合理复核仍由 Bot 决定。宿主只核对精确重复和引用范围，措辞不同的等义指令仍可能重复。[证据契约](../src/LittleLoop.Core/BotEvidence.cs) · [证据投影](../src/LittleLoop.Chat/Bot/BotEvidenceStore.cs)

认知快照提供执行器 ID、能力、权限边界和当前可入队状态。可入队只表示本地配置可用且可以由现有调度器领用，运行权限仍由原生执行器按实际环境处理。选择继续由 Bot 作出，宿主不以任务文本路由执行器。[原生执行契约](../src/LittleLoop.Chat/Bot/BotHarness.cs)

## 复现方法

核心和 SQLite 检查可离线执行。真实试次沿用已配置的认知 API、Codex 和只读 ACP 启动器，运行时使用合成文件及隔离 SQLite。为基线和候选分别构建程序集，供脚本各自复制冻结。每批使用相同种子和相同 10 个输入，配对报告核对驱动、模型配置、夹具与启动器指纹。技术重试定时与 B04 的原验收定时分别核对。保留受控检查、长期任务和在途硬崩溃三个验收来源。[真实接入配置](57-bot-decision-loop.md)

```powershell
dotnet run --project tests/LittleLoop.Checks
dotnet run --project tests/LittleLoop.ChatChecks -- --decision-loop
dotnet run --project tests/LittleLoop.ChatChecks -- --harness
python tests/ChatContinuousLive/autonomy_reliability_batch.py --chat-dll $baselineDll --trials 10 --output data/reliability-live/before
python tests/ChatContinuousLive/autonomy_reliability_batch.py --chat-dll $candidateDll --trials 10 --output data/reliability-live/after --paired-with data/reliability-live/before/batch.json
python tests/ChatContinuousLive/autonomy_reliability_report.py data/reliability-live/before/batch.json data/reliability-live/after/batch.json --output data/reliability-live/comparison.json
python tests/ChatContinuousLive/direct_http_e2e.py --decision-loop inflight-crash
```

费率为同一货币单位的每百万 token 价格，按缓存命中、未命中、输出顺序传给 `--rates-per-million`。报告区分提交到事件账本的调用量和供应商实际账单。未通过结算或审计写入的请求、缺失用量、执行器内部推理不计为已观察成本。

## 2026-11-20 冻结对照结果

旧版 `2853302` 与本次候选版各连续跑 10 次。Chat 程序集 SHA-256 分别以 `37eb826e8c2c` 和 `18a9b1d27b83` 开头。两批使用同一冻结驱动、模型配置、种子、执行器配置和严格断言。逐次观察记录和配对报告位于 `data/reliability-live/baseline-b`、`data/reliability-live/candidate-b` 和 `data/reliability-live/comparison-b.json`。前期探索批次 `baseline-a` 的驱动版本不同。

| 指标 | 旧版 | 候选版 |
| --- | ---: | ---: |
| 严格验收通过／完整目标达成 | 1/10 | 2/10 |
| 独立核对为正确的实质产出 | 3/10 | 9/10 |
| 错误完成 | 2 | 8 |
| 重复执行 | 11 | 1 |
| 结束时需人工输入 | 7/10 | 0/10 |
| 无效草稿／全部观测草稿 | 23/139 | 24/237 |
| 发现缺陷后在同次判断完成修复 | 11/17 | 23/23 |
| 已记账认知 API 请求 | 139 | 237（含 5 条过期审计） |
| 服务返回的总 token | 762,459 | 2,130,269 |

“完整目标达成”查验双执行器证据、实际修订和 30 秒等待等用户要求。“正确产出”只核对产物和最终文字。候选版八次错误完成均漏掉用户的业务定时，其中一次也漏持久化修订。人工等待减少的同时，模型更常在要求未满足时结束任务，结果未达 10/10。费用按当日 DeepSeek Flash 谷价计算，包含全部有用量覆盖的 139 和 237 次观测调用。两个批次推进深度不同，实际供应商账单及 Harness 内部推理费用未核验。[DeepSeek 官方费率](https://api-docs.deepseek.com/quick_start/pricing/)

候选版的 24 个无效草稿包含 20 个 `missing-harness`、2 个 `wake-requires-wait`、1 个 `extraneous-fields` 和 1 个 `invalid-json`。这 20 个委派草稿实际省略了 `harness`，模型之后补上了合法 ID。五个版本过期是独立的提交或修复边界，源记录仍在，未作为坏草稿或修复成功计入。

真实在途硬崩溃在两版均通过。候选版在原生 DeepSeek 已取得实际工具结果、派发日志仍是 `running` 时硬终止隔离服务。新进程保留同一派发及工具证据，仅记录一条 `uncertain` 回执，进入待核对，在途记录清空，没有额外委派或完成。该试次约 18.58 秒，原始结果在 `data/reliability-live/inflight-candidate`。受控验收另有核心回归、102 项 SQLite 决策专项、311 项完整聊天回归和 14 项原生协议检查通过。

## 后续边界

结构校验能确认一次行动有合法的形状与范围，无法确认该行动保留了每项用户要求。下一步可以让 Bot 从用户消息提出带来源的待满足条件，再对比候选动作与当前证据；例如区分等待约定仍待执行、已进入预约和已到期。条件的含义及是否继续由 Bot 判断。可另测基于执行器精确 ID 和动作必填字段的受约束输出，减少修复用量。复测仍应覆盖多种任务和有效复核，避免用固定阶段号解决语义重复。
