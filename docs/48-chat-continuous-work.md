# S1 · 聊天目标与持续工作

2026-11-16 用户确认按持续认知主体方向推进，并明确要求先贯通聊天消息、目标管理、持续调度、补充要求、暂停和恢复。本增量实现该工作闭环；历史模拟工单阶段仍是独立的已实现基础。

## 使用

沿用 `26-chat-phase-c.md` 的 `ChatBot__Policy`、`ChatBot__Data`、`ChatBot__Operators`、`ChatBot__Approvers`。启用 LittleLoop 机器人并以操作员身份发送消息：

```text
任务：修复配置解析的空输入问题，现有测试必须通过。
补充：不要修改数据库结构。
进度
暂停
补充：保留原来的错误提示。
恢复
```

私聊机器人可直接接收这些消息，也识别“帮我修复…”等明确开发请求。群聊和话题只处理 `@littleloop 任务：…` 或回复任务卡的消息，普通群消息不触发工作。多个进行中目标时，回复目标对应的卡片进行控制。`取消` 停止后续工作，不撤销已产生的副作用。

私聊可以直接问问题或交代工作。“帮我查一下近来的黄金价格，整理成 Excel 发给我”走普通对话。加上“任务：”仍按正文选择处理方式。聊天回答和开发任务分开排队，普通对话不会修改已有开发目标。可用工具决定机器人能实际交付什么。

旧版把金价表格之类的请求建成开发任务并等待补充时，升级后可回复当时的追问，也可以在只有这一项待办时直接说明想继续什么。机器人会在普通对话中参考原请求的摘要。仍可对旧任务说“取消”来结束它。

“帮我修复登录问题”会创建开发任务。“开发任务：…”和 `/task …` 可明确指定开发流程。“任务”仍可创建等待补充的目标。回复开发任务可以补充要求，单一任务正在等答复时也可以直接回答。多个任务并行时可回复对应任务消息。“保留原来的错误提示”等明确的补充要求沿用目标版本机制。模型在开发审议中提出的问题会进入等待补充，回答后重新调度。冲突要求保留顺序供模型澄清。

普通私聊真实开发闭环的当前验收见 [私聊真实开发任务](54-private-development-work.md)。`进度` / `查询进度？` 优先查询当前目标；没有活动目标时查询此用户在此会话中最近创建的目标，包括已完成、已取消和待核对任务，不触发重跑。多个活动目标仍须回复任务卡。回复非任务消息不会隐式控制其他活动目标；引文和以“如果”“假如”等开头的讨论不作为任务或补充要求。

网页和 Android 共用普通消息接口。网页任务卡显示目标、版本和补充要求，两端任务状态支持暂停、取消和等待补充。新版“安排开发任务”也创建同一种目标；旧数据库里的历史任务保持原格式，不自动转换。源码审阅机器人仍按原有只读流程运行。

## 状态与存储

`LittleLoop.Core/ContinuousGoal.cs` 定义目标、版本、要求和状态转移；聊天数据库的 `chat_bot_work.goal` 是这些聊天目标的持久化权威状态，`status` 为同事务维护的调度字段。执行目录只保存 agent 会话与工具证据，不另行决定用户目标状态。既有 `LearningSession` / `MultiTaskRuntime` 继续承载开发工具的角色判断、预算和回执。

- 原消息和 `chat_goal_inbox` 在同一发送事务入库，重复客户端消息 ID 复用原消息，不再次入队。编辑旧消息不会追溯改动已经冻结的输入，修改目标应发送补充消息。
- 消费消息时锁定会话和目标，保存新版本、`chat_goal_events` 中的变更或结果，以及 `chat_goal_outbox` 回复，再提交消费标记。
- 发件箱使用固定消息 ID 投递；即使发送成功后进程退出，再投递也不会重复创建回复。会话屏蔽或禁言导致无法发送时跳过通知，不突破聊天权限。
- 修改目标使版本递增。执行器完成时只可更新它执行的版本；旧回执仍保存在执行目录，不能把新要求标记完成。未知副作用会阻止包括新版本在内的继续执行。
- 任务管理要求发起人仍有操作员身份并属于会话。另一个操作员不能修改发起人的目标。审批仍由原审批权限和 nonce 约束，补充消息不授予新工具权限。

数据库升级只增加可空 `goal` 字段及三张表，旧任务仍可读取。结构升级在 MySQL 使用数据库租约，在 SQLite 使用同目录的文件租约。两种存储使用同一目标状态机；适配说明见 [Chat SQLite](52-chat-sqlite.md)。

## 调度、暂停与恢复

后台服务持续处理消息和发件箱；耗时执行单独运行，因此执行期间仍能处理进度查询、补充、暂停和恢复。同一工作区同时只允许一个开发任务执行，防止两个任务修改同一工作区。等待中的任务不主动反复调用模型。独立工作区的并发调度及多目标进度查询见 [S2 聊天多任务协作](55-chat-multitask.md)。

暂停是协作式工具边界暂停：已派发的操作先产生回执，在下一工具请求、审批等待或完成边界检查目标版本。工具边界通过 `turn/interrupt` 请求停止，只有收到对应回合结束事件才记录 `suspended`；断线或未能确认停止按结果未知处理。模型正在生成或外部命令正在执行时，暂停不会承诺立即终止。

恢复使用原执行目录和 agent thread，保留原工具预算、模型轮次数、源码基线与受保护测试。补充要求不能增加预算。待审批请求在安全暂停后失效，恢复后需要新请求。模型提出澄清问题时不进行无意义的自动修复循环。

重启后，已入库的未消费消息、排队目标、等待补充和暂停状态保留；暂停目标不会自行启动。中断时仍标记执行中的目标进入 `needs-reconciliation`，不能通过聊天中的“恢复”绕过核对。若暂停写入数据库但执行器尚未确认停止就崩溃，恢复会检查原 host 状态，拒绝重放未知执行。当前没有新增聊天内的核对/扩权操作。

完成状态继续依赖开发宿主的真实补丁、最终源码快照和必需测试回执；模型总结本身不算通过。用户离线不停止服务端任务，但仍受原有审批、超时和预算约束。

复现集成检查：将 `LITTLELOOP_CHAT_TEST_CONNECTION` 指向预先授权的隔离 MySQL 数据库，名称必须包含 `goal_test`，然后运行：

```powershell
dotnet run --project tests/LittleLoop.ChatChecks
```

检查会创建测试账号与会话，不使用真实聊天账号。数据库管理员需事先创建库并给测试账号授权；检查中的 `CREATE DATABASE IF NOT EXISTS` 仅用于独立测试环境。可另设 `LITTLELOOP_CODEX_EXECUTABLE` 启用真实 agent 夹具检查，其可写范围仅为新建测试项目中的 `code.txt`，测试执行使用固定的检查程序。
