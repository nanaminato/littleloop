# 持续认知主体：目标、阶段与聊天工作闭环

日期：2026-11-16。状态：目标与架构提案，不是实现报告。

后续确认：2026-11-16 用户明确接受此方向，并要求先实现 S1 的消息、目标、持续调度、补充、暂停与恢复。长期方向已确认，不代表所有研究假设与验收阈值已确认。S1 的实现及实测边界见 [聊天目标与持续工作](48-chat-continuous-work.md)；下文保留提案时的现状与候选细节。

## 意图与边界

用户明确提出近期目标：“结合聊天工具，接受用户的消息持续工作”。这确认了能力方向，尚未指定自动触发规则、工作权限或验收阈值。用户提出像人类一样融入社会、持续工作、与人对话、使用工具，并询问是否可作为最终目标；这些长期目标和模拟人类思维的方法保持候选。

建议北极星目标：构建一个具有持续身份、记忆、目标和学习能力的数字协作者，能够在明确职责与权限内，长期参与人类协作，理解交流、使用工具、履行承诺，并根据真实结果改进行为。

“像人类一样”按能力衡量：社会参与看角色、关系、规范和承诺；持续工作看目标延续、调度、恢复与交付；对话看语境、澄清和共同理解；工具使用看选择、组合、验证和迁移。人类意识、主观体验和无限通用能力仍未得到证明。CPU 优先、允许慢、可替换模型及可证伪实验原则继续适用。

## 建议能力路线

以下 S1—S6 是新的能力里程碑，不重编号 `06-design-baseline.md` 的历史五阶段，也不替代聊天 A—D 阶段。阶段可重叠，但验收分别记录。

| 里程碑 | 用户可见结果 | 进入下一阶段的建议证据 |
| --- | --- | --- |
| S1 聊天中的持续工作者（近期） | 对话接任务、追问、推进、暂停、补充、恢复和报告；用户离线后仍在预算内工作 | 下文端到端场景通过；重复消息、重启和旧回执不造成重复副作用或目标覆盖 |
| S2 多任务协作者 | 工作中仍能答复；管理多个目标、依赖、优先级与承诺 | 多任务混合负载下无永久饥饿；取消和目标变更可追踪；单角色调度与聊天队列一致 |
| S3 具有长期记忆的熟练工作者 | 跨会话记住许可范围内的偏好与经验，重复任务更可靠 | 与无记忆基线比较，在留出任务上测得成功率或成本改善；错误记忆可纠正，私有记忆不跨会话泄漏 |
| S4 可迁移的工具使用者 | 依据能力说明学习组合新工具，适应新项目和环境变化 | 未见工具或项目中的任务可完成；记录泛化失败、预算和副作用；权限变化立即生效 |
| S5 社会协作参与者 | 理解不同人的职责、群体语境、承诺与冲突，能协商和交接 | 多人冲突需求、授权变更、信息可见性及承诺到期场景通过；明确数字身份，不靠假扮真人验收 |
| S6 持续成长的认知主体（研究） | 自评估能力缺口，提出并验证技能、策略或模块改进 | 独立评测反复证明收益，记录退化并可回退；自我描述与实际能力一致 |

统一报告任务成功率、误执行次数、重复副作用、恢复成功率、响应延迟、模型/工具成本和人工干预次数。阈值应在 S1 基线试运行后确定并冻结，不用单个成功演示代替长期证据。建议先完成一次 24 小时混合事件试运行，再扩展至 7 天；这是候选验收方案，尚未完成。

## 中间层：借鉴认知功能，保留清晰契约

这些是逻辑职责，不要求新建八个项目或八个服务。优先复用现有内核和工具。

| 层 | 职责与持久化结果 | 类似人的哪种能力 |
| --- | --- | --- |
| 事件与身份 | 标准化消息、工具结果和计时事件；保存来源、主体、会话、事件 ID 和可见范围 | 知道谁在什么场合说了什么 |
| 对话与意图 | 区分闲聊、提问、任务、补充、取消、反馈；歧义保留并追问 | 理解话语意图 |
| 目标与承诺 | 保存目标、验收、负责人、授权、截止时间、依赖、版本和完成证据 | 记住答应做什么 |
| 情境与工作记忆 | 维护当前事实、未知项、假设、进行中的计划；按权限检索相关长期记忆 | 保持当前思路 |
| 注意力与调度 | 在新消息、原任务、工具回执和期限之间分配有限计算；等待任务不占住整个主体 | 切换注意力 |
| 审议与规划 | 形成候选，比较约束和成本，选择行动、询问、等待或拒绝 | 推敲下一步 |
| 行动与验证 | 工具适配、权限校验、幂等、回执、对账和独立结果验证 | 动手并检查结果 |
| 长期记忆与反思 | 分开保存经历、事实、技能和偏好；经验先作为候选，经评测后采用 | 形成经验并纠错 |

身份、权限、预算、版本和审计贯穿所有层。事实、模型推测、用户要求与工具结果分别保存；模型输出不直接变成事实或授权。决策记录保存可审查的依据与行动结果，不要求记录模型私有思维过程。

最小闭环：消息事件 → 意图提案 → 目标事务 → 选择下一个可推进目标 → 规划与授权校验 → 工具回执 → 验收或调整 → 聊天反馈。新消息可随时进入这个循环；空闲时等待事件，只有获准的期限检查、重试或整理才唤醒，避免无目的持续调用模型。

初期无需完整情绪系统、潜意识模型或大脑分区仿真。可先实验“快速规则处理明确请求，较慢审议处理未知情况”，以错误率和成本判断是否有价值。内部状态变量若引入，也需要对照实验证明作用。

## S1 可交付范围

先支持现有 LittleLoop 聊天中的受限开发任务，复用当前项目策略、工具回执和审批。默认建议私聊机器人接收自然语言；群聊仅对明确指向机器人的请求或现有任务动作响应。群触发规则仍待产品决策，普通消息不会因本文件自动获得执行授权。

建议增量顺序：

1. 消息接入统一事件，保留用户、会话、来源消息、去重键和任务关联；建立意图路由。先贯通单个受限任务。
2. 目标账本支持补充、状态查询、暂停、恢复和取消；变更带预期版本，更新验收条件时保留历史。
3. 持久化工作循环连接既有运行时与开发执行器；模型与工具调用异步返回，等待审批或回答时让出注意力。
4. 增加重启恢复、工具对账、消息发件箱和有界通知；验证完成后才发送交付结论。

任务状态建议包含：就绪、执行中、等待回答、等待授权、暂停、待核对、已完成、失败、取消。事件可以恢复等待任务；执行结果未知必须先核实，不能直接重跑。取消阻止新派发，已发生的副作用另行说明。

接入时的关键矛盾：现有聊天机器人等待整个工作结束，而多任务内核已经有独立消息入口；必须确定唯一任务状态所有者，避免两套队列分别宣布完成。建议核心持有目标版本和行动状态，聊天数据库持有消息及任务投影，使用持久事件/发件箱同步；数据库与文件状态之间的崩溃窗口要专门验证。这是方案，不是现有事实。

S1 端到端验收场景：

- 用户发送受限修复目标，系统澄清缺失验收项，保存任务并推进，回传实际测试结果。
- 工作期间查询进度得到当前状态；补充要求关联原任务并递增版本，旧结果不能覆盖新要求。
- 同一消息重复投递只建立一个任务；群聊普通聊天不触发工作，其他会话不能读到私有任务。
- 等待回答或授权时不反复调用模型；用户回复后继续原任务，预算耗尽时明确等待。
- 用户退出客户端后服务继续工作；服务重启后恢复可恢复项，对不确定副作用进入待核对。
- 用户暂停或取消后不再派发新的动作，最终报告区分已做、未做和仍不确定的结果。

## 尚需明确的产品选择

长期“社会参与”的初始范围是项目团队还是个人助手；一个角色服务多人时谁能改变共同目标；跨私聊与群聊允许共享哪些记忆；无人交互时允许哪些自主工作。这些不阻止设计 S1 的受限闭环，但不能被推定为已经授权。

本文件和 Singularity 模型用于项目构建追溯；运行时的目标、承诺与认知记忆应存入产品运行状态，不能直接写进项目模型充当运行数据库。
