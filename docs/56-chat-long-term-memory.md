# S3 · 私聊长期记忆

## 现在如何在私聊中使用

可以直接说“以后做完告诉我结果就行”，也可以在一个进行中的任务里说“这次完成通知附上原任务目标”。前者设置本私聊的默认值，后者关联到具体任务。如果同时有多个任务，回复其中一张任务卡即可指定。连续三个不同任务作出相同的单次选择，或对三个已发送的完成通知给出相同反馈，系统会询问是否设为默认。回复该建议即可确认或拒绝。消息重试及反复纠正同一任务只算一个样本。

用户可以说“这类文档的尾随空格有意义”。之后处理另一份样稿时，LittleLoop 会从该消息取回保留行尾空格的做法。如果新任务明确要求清理行尾空格，就按当前要求处理。也支持开放主题的条件表达，例如“以后处理发布说明时，先核对版本号”或 “When preparing release notes, check the version first”。这种教学无需先发送“启用经验”。同一主题的新做法取代旧版本。使用“查看经验”查看来源，回复自己的来源消息并发送“撤回经验”即可撤回。编辑或删除来源会使这项做法失去召回资格。

“启用经验”另行开启从已验收补丁自动提取文件线索。“停用经验”暂停项目做法的写入与召回，也会关闭自动补丁学习。重新启用后，可继续使用仍有来源的记录。早期命令及已保存的偏好和补丁经验仍可使用。

## 如何形成执行上下文

| 环节 | 责任与取舍 |
| --- | --- |
| 理解当前话语 | Core 从独立陈述提取主题、值和时效。讨论、引用、问题和单次要求与长期教学分开处理。格式与通知有结构化含义，条件做法保留用户给出的动作原文。 |
| 持久化 | 消息消费、来源、活动任务变更及回复在同一数据库事务内提交。偏好按账号和私聊保存；项目做法还绑定当前项目授权摘要。来源冲突时，同一主题取最新有效写入，撤回不会复活被覆盖的版本。 |
| 检索 | 首次派发默认开发任务时，先核对会话、操作员、项目授权、任务版本与来源。最近 64 条教导中最多选 3 条，文档专用规则优先于通用默认。补丁经验先查精确目标，再从最近 32 项比较动作、对象、字面参数及约束；同分且指向不同路径时放弃近似命中。执行前过滤已经移走或失去许可的路径。 |
| 执行 | 提示中给出来源消息和适用做法，当前要求优先。工具许可、补丁审批、最终验收沿用开发宿主。已提交给执行器的历史提示仍可复盘。 |

默认在本地使用确定性策略。部署时可将环境变量 `ChatBot__MemorySemantics` 指向一份本机语义模型配置文件，参考 [Ollama 配置](../examples/models/ollama.template.json) 并填入实际安装的模型。仅接受回环地址。规则未命中且有可见的已教做法时，适配器可对最多八项候选做一次语义选择，例如从不同措辞辨认同一类交付物。模型须返回既有来源编号和当前任务的原文片段；宿主复查版本、来源及可见性后才采用。超时、无匹配和无效回复均可继续原任务。模型调用期间不占用数据库事务，单次超时上限为八秒。

2026-11-19 用户确认按自然纠正、跨任务召回及当前要求优先的思路实现，并允许按需要重构项目。三个独立样本、候选检索上限以及语义适配方式是工程选择。下面保留早期精确匹配版本的设计与配对实验，便于对照。

## 本版验证

运行 `dotnet run --project tests/LittleLoop.Checks` 验证纯策略与既有核心行为。运行 `dotnet run --project tests/LittleLoop.ChatChecks` 验证普通消息收件箱、任务领取、真实提示构造和通知发件箱。核心检查通过 356 项。使用同一冻结版程序集，SQLite 和隔离 MySQL 测试库分别通过 190 项聊天检查；运行日志为 `data/generalized-memory-chat-final.log` 与 `data/littleloop_goal_test_memory_41dec80c0f.log`。语义选择器使用受控响应，覆盖跨措辞选择、伪造来源、虚构引用、当前要求相反，以及模型回复前用户删除来源。

真实 Codex 验收入口为 `python tests/ChatContinuousLive/direct_http_e2e.py --memory`。先构建 Chat 并设置 `LITTLELOOP_CODEX_EXECUTABLE` 为已登录的 Codex 程序绝对路径；可用 `LITTLELOOP_CHAT_DLL` 指定构建产物。驱动在随机端口启动独立服务和 SQLite 数据库。用户通过普通消息教一个随机生成的发布编号前缀。服务重启后，三个任务各开一个 Codex 会话，通过受限宿主工具修改夹具文件。前缀没有预先写入项目或测试脚本，驱动另行核对最终文件。

## 未见私聊任务的泛化评测

运行 `python tests/ChatContinuousLive/direct_http_e2e.py --memory-generalization`，以 `LITTLELOOP_CHAT_DLL` 指向部署产物。评测用独立的 SQLite 聊天实例和合成工作区。先通过私聊教授带随机前缀的做法，包含更正和撤回，再重启服务并给每项新任务创建独立的 Codex 会话。测试材料包括交接、验收、巡检、更新日志等主题，覆盖直述、近义改写、跨语言、同词异义、当前要求冲突和多个主题。运行期间没有向现有服务的会话投递实验任务。

每项任务分别核对首次 Codex 请求的来源编号和最终文件的实际内容。宿主测试检查文件是否按夹具形态更新，独立断言检查随机前缀、文件内容和保护文件。结合这两项可以区分漏召、误召、正确召回后执行器未采用以及误召真正改变文件。评测针对部署时的默认本地匹配。它覆盖固定格式的项目做法，适合复现失败类型。

以 13 个留出场景为单位，首次请求的来源集合完全正确的是 **8/13**。应召回的任务完整召回 **5/8**，应抑制的任务正确抑制 **3/5**。13 项均完成并通过宿主测试，独立文件校验通过 **8/13**。两项误召均进入提示，最终文件仍符合当前要求。两项来源完全正确的任务未采纳提示。

| 场景 | 真实观察 |
| --- | --- |
| 英文单复数、既有中英别名、需求包含两个相关主题 | 设备巡检、更新日志和双主题任务带入了所需来源，实际写出正确编号。 |

| 肯定式当前覆盖 | 当前明确指定 `VIP-`，旧验收单前缀仍进入提示。Codex 最终写入 `VIP-108`。直接说“这次不要添加编号前缀”的试次正确抑制旧经验。 |
| 主题只用于描述另一个交付物 | “验收单模板使用手册”误召了验收单规则。Codex 最终为手册写出本次要求的纯数字。 |

单独调用同一发布版 Core 还复现了三个边界。补丁经验能将“修复登录超时”和 “Fix sign-in timeout”匹配为 85 分。换成“排除登录超时故障”得到 0 分。对调“关闭页面通知、打开登录提示”中两个动作对应的对象，仍得到 94 分。条件经验中，“性能报告”和“内网性能报告”两条冲突规则也可匹配同一项内网任务。这些是检索层探针，未计入 13 个真实私聊场景。证据见 `data/continuous-deployment/generalized-memory-core-probe.json`。

首次夹具的一条退货任务漏写了预期前缀，已保留原记录并补跑写明前缀的任务。模型容量退避导致部分试次未能完成，已用同版 DLL 和同一模型配置在隔离服务补跑。结果按场景选取有完整证据的一次，原始取消和未派发记录仍可查。综合结果、补跑来源和三份程序集哈希见 `data/continuous-deployment/generalized-memory-evaluation.json`。实际模型为 gpt-6-astra，推理强度 low。

## 设计

首版聚焦两类用户可以核对的记忆。偏好由用户明确写入，首个偏好是完成通知是否附带原任务目标。经历来自既有任务账本，用户可以回顾本私聊最近三项通过宿主验收的目标。回顾只展示目标和任务消息序号，便于追溯原任务卡。

偏好以会话和账号为联合主键，记录最近更改所对应的消息序号。记忆命令与消息消费标记、回复共用事务。完成通知在结果事务中读取当时生效的偏好，成文后进入既有发件箱。更正适用于之后生成的通知，历史通知和聊天消息按原规则保留。普通消息、任务描述和模型回执都不自动写入偏好。

记忆命令仅在启用 LittleLoop 的私聊中由任务操作员使用。群聊和其他私聊各自隔离。偏好只影响通知呈现。历史任务回顾与下面的经验提炼分别使用任务账本与宿主验收回执。

## 使用

- `记住偏好：完成通知含目标` 或 `记住偏好：完成通知简洁`
- `查看偏好`
- `忘记偏好`
- `回顾经验`

无偏好时发送简洁通知。忘记偏好会删除持久设置，原来的聊天消息仍可在会话历史中看到。

## 自动提炼与复用

在私聊发送 `启用经验` 后，默认 Codex 执行器完成并通过宿主验收的目标会自动提炼最多三个成功补丁的相对文件路径。记录源任务及版本、项目授权摘要、目标及要求的摘要。旧记录、取消或过期版本、缺少补丁回执的结果不生成经验。

同账号、同私聊、同项目授权、同目标及要求的新任务在首次派发时可得到最近一条匹配经验。经验建议先读这些文件，用当前内容重新判断；提示只携带路径和来源，补丁、命令、模型报告、旧哈希和旧审批不随经验传递。附带引用或上下文锚点的任务及已有执行会话的恢复沿用原流程。源消息被删除后停止检索该经验。

`查看经验` 可列出本私聊最近的经验来源。回复源任务卡发送 `撤回经验` 会删除该项，必要时可撤回较旧的同类记录。`停用经验` 会暂停本私聊之后的提炼和复用。已经提交给执行器的提示保留原执行记录。

## 后续评测

首版对照比较同一类任务在有偏好和无偏好时的通知内容，检查重开连接后是否继续生效，以及更正、忘记和会话隔离。

本地构建无警告。`dotnet run --no-build --project tests/LittleLoop.ChatChecks` 在 SQLite 上通过 142 项聊天目标检查。新增场景使用受控回执，验证重开数据库、重复提交、纠正、遗忘以及不读取其他账号或群聊的已完成任务。MySQL 和真实代理的实测留待后续。

经验闭环增量将同一测试套件扩展至 150 项。新增对照覆盖关闭经验与启用后的提示差异、成功补丁路径投影、重启、授权变化、补充要求、跨私聊隔离和撤回。测试使用受控回执和实际提示构造。

后续可在有记忆与无记忆两组使用同一模型、工具权限和预算，比较独立验收通过率、工具调用次数、成本及需用户纠正的次数。当前的严格匹配只验证闭环，泛化到未见过的同类目标需要独立评测。

## 真实 Codex 配对评测

使用提交 `86b8545` 构建，运行隔离的 SQLite 聊天服务、默认 Codex 适配器和合成文本项目。页面状态与横幅标志各完成一次训练任务，各用两个未参与训练的初始值复测。每个初始值分别在经验开启和关闭时执行一次，两种顺序各两对。两组使用同一目标文本、初始文件、工具权限、预算、宿主验收与独立文件校验。所有任务从新的 Codex thread 开始。开启组从实际请求核对提示与训练来源，关闭组从请求核对没有经验提示。每个开启组任务完成后撤回该次新经验，使后续试验继续使用原训练来源。

工具次数以 App Server 的 `item/tool/call` 请求计数，包括未成功的请求。用量取每个新 thread 的最终累计 `thread/tokenUsage/updated`，分别记录缓存输入、非缓存输入和输出。训练任务单列。该接口未提供本次运行逐项实际扣费，令牌用量用于对照，无法直接换算账单。
