## 目标账本

继续使用 `ContinuousGoal` 的 `Objective`、`Requirements`、版本和生命周期。Bot 将用户消息中的独立要求写成结果、行为、时间、约束或通知条件。每条条件保留稳定 UUID、原始消息序号、目标和创建版本、描述、状态、替代关系及最近评估。快照内的状态包括 `Pending`、`InProgress`、`Satisfied`、`Unknown`、`Superseded` 和 `Withdrawn`。原 `chat_goal_events` 同时保存每次写入的完整目标快照，原 `chat_bot_events` 保存决策、拒绝的草稿和证据事件。没有新增数据表或独立生命周期。[条件协议与投影](../src/LittleLoop.Core/GoalObligations.cs) · [原目标存储](../src/LittleLoop.Chat/Bot/ChatGoalStore.cs)

创建目标与首轮委派一起提交条件。收到修订时，Bot 在 `Revise.instruction` 保留用户原有约束文本所需的上下文，并在 `obligationEdits` 明确新增、替代或撤销。删除或替代需要当前用户消息和理由。未修改的有效条件沿用原 ID。用户消息的领用、原文本修订、条件变更、账本事件和待发通知使用同一事务。提交前锁定会话，复核权限、版本、当前消息与证据。在途 Harness 的迟到回执留在旧派发版本，不能满足之后新建的条件。冻结驱动沿用文本修订与实际收件人观察，现有 Harness 仍使用原目标提示。[提交与回执事务](../src/LittleLoop.Chat/Bot/BotActionStore.cs) · [提交门与恢复](../src/LittleLoop.Chat/Bot/BotDecisionStore.cs)

引用活跃目标的用户消息只能修订对应目标。协议拒绝跨目标写入、直接完成、预约和委派。Bot 可以明确处理用户要求的目标控制或处理适用的记忆操作。信息性 `Reply` 必须说明为什么不改变目标，输出同时注明目标要求未变更。定向修订草稿耗尽时，现有目标记录未核对的来源序号，后续由 Bot 根据原文解决。存在未核对来源的目标不能完成。旧任务保持 `obligations: null`，直到 Bot 根据可见的原始用户消息与修订历史初始化。缺少可见来源或证据时，Bot 可以询问用户。普通房间成员无法从任务详情读取内部条件证据。[来源和持久证据核对](../src/LittleLoop.Chat/Bot/BotObligationStore.cs) · [任务详情访问范围](../src/LittleLoop.Chat/Bot/ChatBotEndpoints.cs)

## 从预约到完成

Bot 用 `Wait` 绑定活动的时间条件。调度器将检查 ID、到期时间和目标版本保存在原有唤醒记录中，条件先进入 `InProgress`。恢复时读取同一检查，真实到期才经 `IBotDecisionEngine` 交给 Bot，记入与提交决定同一事务。暂停、取消、修订和完成沿原有版本围栏使旧预约失效。到期事件能证明按时有资格复查，工作要求的额外读取或判断还需要 Bot 寻找实际证据。

Bot 可在 `Delegate`、`Wait` 或 `Complete` 中评估活动条件。满足评估需要理由及现有派发和事件引用，时间条件需要真实到期检查 ID。宿主核对归属、版本范围、执行边界与证据类型，并在仍有在途派发时拒绝完成。超出对话窗口的引用仍可在原账本核对。结果条件只能使用可归属的成功事实，明确要求观察失败时，行为或约束条件可引用实际失败的工具事件。权限拒绝和未知执行不提供这种证据。通知条件可与 `Complete` 一起用实际消息和启用的通知设置提交，支持的是消息进入既有发件箱。送达由独立验收检查。只要仍有活动条件未满足或来源未核对，提交返回结构化错误。Bot 可以继续委派、等待或根据真实用户意图提出修订。[条件核对](../src/LittleLoop.Core/GoalObligations.cs) · [派发和回执证据](../src/LittleLoop.Chat/Bot/BotEvidenceStore.cs)

## 草稿修复

三次尝试的生产预算维持原值。每份修复请求带上相同的有效条件与原始来源，同时提供上一份可解析草稿的限长意图和结构化错误。对可唯一绑定的已有时间条件，修复不得静默缩短或删掉拟议等待。Bot 可保留原等待，或说明为何先委派并让该条件保持开放。创建与修订首稿中已通过来源及字段核对的条件编辑也需保留。语义改变仍需用户来源的明确修改。原始草稿、格式规范化和接受或拒绝结果留在原事件账本。修复不会授予权限或伪造回执。[模型适配器](../src/LittleLoop.Tools/ModelBotDecisionEngine.cs)

当前继续使用 Chat Completions 的 JSON Object 模式，支持合法 JSON 形状。动作需哪些字段、条件是否覆盖用户意图、证据是否能证明用户要求仍需分别处理。DeepSeek 的严格函数调用走另一协议，可在独立配对试验比较格式拒绝率、请求数和费用，本轮未改变供应商配置。[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/) · [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)

## 语义边界

- 原始消息与条件同时可查，可以审计拆分是否漏项。宿主无法证明一个自然语言拆分已经穷尽用户意图。无引用且有多个活跃目标时，目标绑定依赖 Bot 的判断或澄清。
- 检查的到期证据不证明真实重读、跨阶段顺序或多步结果。Bot 仍需据用户要求拆出这些行为并核对执行事实。现有时间条件记录相对延迟，语义上的起算阶段留给 Bot 判断。
- 派发和事件有作用域及因果边界。一个相符的引用只证明该记录存在且可用，对复杂输出等价性、外部副作用和证明充分性仍需认知判断。通知进入发件箱也不能证明用户已阅读。
- 现有目标经首轮 `Delegate` 建立，单纯先等待再执行的全新目标以及同一时刻多个独立预约未在本轮实现。
- 删除或编辑待核对来源后，旧原文按会话可见性隐藏。仍需设计后续用户如何明确消解该来源的协议。长历史旧目标的初始化也受模型上下文预算约束。

下一步先区分通知、工具事实与到期检查的草稿形状，并让校验反馈说明冲突字段和可用引用。对跨阶段与全程要求，允许 Bot 概括一组有因果顺序的事实，并单独测量计划是否履行已登记的约束。下一轮仍用同一严格长任务对照，以正确产出和人工等待同时检验改善。
